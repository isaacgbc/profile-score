<objective>
Wire the Apify scrape path into the existing 11-stage audit orchestrator with minimal-risk Strategy A from 01-RESEARCH.md §Orchestrator Stage 2 Integration:
1. Extend `AuditInput` with two optional fields: `preparsedLinkedinSections?: Record<string, string>` and `linkedinProfileSource?: "paste" | "apify" | "pdf"`
2. Extend the shared audit request schema in `src/app/api/audit/generate/shared.ts` to accept these fields from the route body
3. Patch Stage 2 in `audit-orchestrator.ts` to bypass `parseLinkedinWithStructuring` when preparsed sections are provided
4. Patch the orchestrator's prompt preflight to pick new `audit.linkedin.system.apify` / `rewrite.linkedin.section.apify` versions when `linkedinProfileSource === "apify"`, falling back to existing prompts if the apify variant is missing
5. Add `scraping_profile` to the `ProgressStage` type union (consumed by `GenerationProgress.tsx` in Plan 01-09)
6. Seed 4 new PromptRegistry rows (audit + rewrite, en + es) via `prisma/seed.ts`
7. Integration test: orchestrator with preparsed sections produces output identical in structure to the paste path (LLM calls mocked)

Purpose: This is the critical integration point that makes the Apify path actually drive the audit. After this plan, the full pipeline works end-to-end once the UI is wired in Wave 3. Stages 3-11 stay untouched because the `linkedinSections: Record<string,string>` contract is preserved.

Output: Orchestrator + shared schema + route patched, new progress stage, new prompts seeded, integration test proves the bypass path works.
</objective>
