<objective>
Install `apify-client` and build the Apify scraper service module: a thin wrapper around `ApifyClient.actor().call()` with (a) a dedicated circuit breaker instance, (b) a dedicated rate limiter bucket, (c) typed error codes matching `.claude/rules/api-routes.md`, (d) integration with `logError()` for fire-and-forget observability, (e) private-profile detection (empty items -> `APIFY_PROFILE_PRIVATE`), and (f) cost reporting via `run.usageTotalUsd` fallback to hardcoded `$0.004`.

Everything about calling Apify (token management, timeout, circuit breaker, error classification) lives in ONE module so the API route (Plan 01-07) and orchestrator (Plan 01-08) never import `apify-client` directly. All failure modes produce typed errors the route can map to localized error keys.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Route handler -> scraper client | `profileUrl` passed as already-normalized string; `requestId` for logs |
| scraper client -> Apify API | HTTPS call with Bearer token; scraper client is the only module that sees the token |
| Apify response -> scraper client | Untrusted external payload; validated via harvestProfileSchema with `.passthrough()` |
| scraper client -> error logger | Sanitized `inputMeta` (urlHash, durationMs) — never raw URL or profile content |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-01 (T-03: Apify API token exposure) | Information Disclosure | `APIFY_API_TOKEN` | mitigate | Read from `process.env.APIFY_API_TOKEN` inside function body; NEVER prefixed `NEXT_PUBLIC_`; NEVER logged via `console.log` or `logError` (no `token` key in inputMeta); module fails loud at call time (not module load) so CI/build never needs the real token. |
| T-04-02 (T-06: cascading failure when Apify is down) | Denial of Service | `apifyCircuitBreaker` | mitigate | Dedicated breaker with `failureThreshold: 0.6`, `cooldownMs: 20000`. When OPEN, `allowRequest()` returns false and the client throws `APIFY_CIRCUIT_OPEN` without ever calling Apify. Test 7 enforces this. |
| T-04-03 (T-07: log injection via profile text) | Tampering | `logError` inputMeta | mitigate | Only hashes and numeric durations go into inputMeta. NO raw profile strings, NO raw URLs. `urlHash` is a 16-char SHA-256 prefix — safe for log format strings. |
| T-04-04 (T-12: cost abuse via high-volume scrape) | Denial of Service / cost | `scrapeRateLimiter` | mitigate | `createRateLimiter({ windowMs: 60_000, maxRequests: 3 })` caps per-key rate at 3/min. Combined with fingerprint quota (Plan 01-06), worst-case cost per key is $0.012/min. Test 1-3 enforce. |
| T-04-05 (T-02: PII exposure via error logs) | Information Disclosure | Error branches | mitigate | Failure branches never include the full response payload or scraped items in `logError.inputMeta`. Only `durationMs`, `transient` flag, and `urlHash`. |
| T-04-06 (empty items conflated with success) | Information Disclosure via wrong error UX | Private profile detection | mitigate | Test 4: empty items OR missing `headline` throws `APIFY_PROFILE_PRIVATE`. Route maps to 422 + i18n key `apify.error.private`. |
</threat_model>
